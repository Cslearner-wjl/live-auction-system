## 0. 演示前置与环境清理

```powershell
# 若生产 Compose 正在占用 3000 端口，先停掉（dev server 才能起来）
docker compose -f docker-compose.prod.yml down

# 确认端口 3000 已释放（应无输出）
cmd /c "netstat -ano | findstr `":3000.*LISTEN`""
```

**讲解词：** 本系统是一套面向抖音直播电商场景的全栈竞拍系统，覆盖「商品上架 → 规则配置 → 直播间展示 → 实时出价 → 动态排名 → 竞拍结束 → 成交订单 → 模拟支付」完整闭环。技术栈是 pnpm monorepo：React 管理后台 + React 移动端 H5 + NestJS 后端 + MySQL/Prisma + Redis + Socket.IO。

## 1. 基础设施启动

```powershell
# 启动 MySQL 和 Redis
docker compose up -d mysql redis

# 等待 healthy（约 10-15 秒），确认两个容器均为 healthy
docker compose ps

# 生成 Prisma client + 跑迁移 + seed 演示数据
pnpm --filter @live-auction/server prisma:generate
pnpm --filter @live-auction/server prisma:migrate
```

**讲解词：** 数据层用 MySQL 保存权威业务记录，Redis 承接高频出价热状态、分布式锁和排行榜。seed 会清理历史演示数据并准备 `room_1`、`admin_1`、`user_1/2/3` 等 demo 身份。

## 4. 演示主线（建议 5 分钟）

### 第 1 分钟 — 项目背景与架构

**讲解词：** 三个设计要点 ——
1. **状态机集中**：所有竞拍状态流转只在 `AuctionStateMachineService`，UI 和网关都不复制业务规则；
2. **Redis 承接热出价**：Redis Lua 脚本单次原子完成「状态 / 价格 / 加价幅度 / 防狙击 / 封顶」校验和热状态更新；
3. **outbox + snapshot-first**：出价先落库再广播，WebSocket 只做通知，客户端重连后以 snapshot 为权威恢复。

### 第 2 分钟 — 后台创建商品 + AI 参考 + 配置规则 + 启动

| # | 操作 | 验证点 |
| --- | --- | --- |
| 1 | 打开 `http://localhost:5173/admin/items/new` | 创建页正常加载 |
| 2 | 填写商品名、介绍、卖点，上传本地图片 | 表单校验通过，图片自动填入 `/uploads/items/...` |
| 3 | 配置规则：起拍价、固定加价、封顶价、时长、防狙击窗口、延时时长、最大延时次数 | 规则字段正常（金额前端按元填写，提交时转整数分） |
| 4 | 点击「AI 生成竞拍参考」 | 返回适合人群、卖点话术、参考价格区间、风险提示；`source=mock`（无 Key 时） |
| 5 | 编辑 AI 输出，点击「应用建议卖点 / 起拍价 / 封顶价」 | 对应表单字段被 AI 建议覆盖 |
| 6 | 提交创建竞拍 | 创建成功，列表出现 `SCHEDULED` 竞拍，AI 参考已绑定 |
| 7 | 在列表点击「启动」 | 状态变为 `RUNNING`，记下 `auctionId` |

**讲解词：** `POST /admin/auctions/with-item` 在**单个事务**内创建商品、规则和 `SCHEDULED` 竞拍。AI 参考由后端先用 `PriceInferenceService` 推断整数分价格区间，再由 Mock/OpenAI/Ark 生成文案 —— **价格字段始终由后端覆盖**，模型只影响文案，密钥只在后端读取。

### 第 3 分钟 — 移动端多用户真实出价

打开 2–3 个移动端窗口（替换上一步的 `auctionId`）：

```txt
http://localhost:5174/?roomId=room_1&userId=user_1&auctionId=<auctionId>
http://localhost:5174/?roomId=room_1&userId=user_2&auctionId=<auctionId>
http://localhost:5174/?roomId=room_1&userId=user_3&auctionId=<auctionId>
```

| # | 操作 | 验证点 |
| --- | --- | --- |
| 1 | 三个窗口进入直播间 | 拉取 snapshot，展示竞拍卡片、当前价、倒计时、排行榜、AI 参考卡片 |
| 2 | user_1 出价 | 自己看到「当前最高价」，其他窗口实时看到当前价上涨和排名变化 |
| 3 | user_2 出价超越 | user_1 收到「你已被超越」，排行榜实时更新 |
| 4 | 重复点击同一出价按钮 | `clientBidId` 幂等，不产生重复出价 |
| 5 | 刷新某个窗口（模拟断线重连） | 重新加入房间，重拉 snapshot 恢复当前价 / 排名 / 倒计时 |

**讲解词：** 出价走真实 `POST /auctions/:auctionId/bids`。服务端先进本进程 `auctionId` 队列，再取 Redis 分布式锁，保证「Redis accepted → DB 落库」关键段串行；落库后写 `AuctionEvent(BID_ACCEPTED, PENDING)`，由 outbox 发布器 claim 后定向广播到 `auction`/`room`/`user` 房间。移动端按 `serverSeq` 丢弃旧事件，跳号时重拉 snapshot。

### 第 4 分钟 — 防狙击延时 / 封顶成交 / 订单生成

| # | 操作 | 验证点 |
| --- | --- | --- |
| 1 | 在倒计时最后窗口内有效出价 | `endTime` 延长，广播 `AUCTION_EXTENDED`，倒计时回弹 |
| 2 | 出价达到封顶价 | 立即通过状态机成交 `ENDED_SOLD` |
| 3 | 或等待自然到期 | 有最高出价人 → `ENDED_SOLD`；无人出价 → `ENDED_UNSOLD` |
| 4 | 成交后中拍用户结果弹窗 | 显示订单号，唯一订单（`Order(auctionId)` 唯一约束） |
| 5 | 点击模拟支付 | 调用 `POST /orders/:orderId/mock-pay`，订单状态更新 |
| 6 | 后台订单列表 | 看到成交金额、买家脱敏名、订单状态 |

**讲解词：** 结算在 DB 事务内用 `WHERE status = RUNNING` 条件更新，配合 `Order(auctionId)` 唯一约束，杜绝多实例或重复 timer 造成的重复结算 / 重复订单。

### 第 5 分钟 — 技术亮点与工程材料

**讲解词：** 收尾展示 —— Redis Lua + 分布式锁的并发一致性、outbox claim/lease/死信、snapshot-first 重连恢复、真实 30/100 并发 HTTP 压测与 100/1000 Socket.IO 连接压测、AI 旁路安全设计，以及完整的测试 / 文档体系。

## 6. 性能压测（可选，需 Docker 已启动）

```powershell
# HTTP 并发出价基线（自动建用户/竞拍、并发出价、校验一致性）
pnpm perf:day12

# 100 并发
$env:DAY12_BID_ATTEMPTS='100'; pnpm perf:day12; Remove-Item Env:DAY12_BID_ATTEMPTS

# Socket.IO 连接压测
pnpm perf:socket
$env:SOCKET_CONNECTIONS='1000'; pnpm perf:socket; Remove-Item Env:SOCKET_CONNECTIONS
```

已记录基线：

| 场景 | 结果 | 一致性 |
| --- | --- | --- |
| HTTP 30 并发 | accepted 24/30，p95 873.41ms | 通过 |
| HTTP 100 并发 | accepted 80/100，p95 3516.74ms | 通过：当前价/最高出价人/订单一致 |
| Socket.IO 100 连接 | 连接/join/snapshot/PING-PONG 100% | 通过 |
| Socket.IO 1000 连接 | 连接/join/snapshot/PING-PONG 100% | 通过 |

**讲解词：** 100 并发本机 p95 约 3.52s，体现「一致性优先于吞吐」的取舍 —— 同场竞拍引入串行锁保护会增加尾延迟，但保证了当前价单调、最高出价人唯一、无重复订单。这是本机 dev 数据，不作为生产承诺。
